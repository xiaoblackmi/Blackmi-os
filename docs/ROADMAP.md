## 当前优先级
| 阶段 | 任务 | 验收门槛 |
|---|---|---|
| P0（完成） | 恢复版本基线 | PR #1 已将 V3.1.3/V3.2/V3.2.1 合入 main，核对最新 HTML blob 与分支一致 |
| P1 | 稳定性与体验回归 | 834×360 消息输入框可正常输入，键盘/按钮不挤压，复测 V3.1.3 已有修复与用户可见版本统一；通信协议保持不变；目标 PAD 实测 |
| P2 | V3.3 三国身份战 | 独立规则模块与 UI，复用现有大厅，优先少量原创角色/卡牌与完整回合、响应、胜负、隐藏身份流程；明确人数与规则范围；规则测试、私有状态隔离、观战、2/4/8 台适用规模逐级验收（具体人数按规则） |
| P3 | 性能及发布 | 比较文件大小、帧时间、内存、既有游戏回归；不引入外部运行依赖；核验后再更新 README 下载指针 |

V3.3 首版建议以回合制、无重型资源、独立名称及原创卡面实现；不开局前承诺完整商业游戏规则。身份与手牌必须由房主按玩家分别下发，观战者不得接收。规则流程、人数、角色技能和素材方案须在实现时明确。项目许可证尚待所有者确定；不得未经授权使用商业游戏品牌/原画/音频或第三方代码。参照 [SDK](../SDK.md) 与 [测试门槛](../TESTING.md)。

## 暂缓：历史 ESP32 常驻 Core 与 AI 方案

下列为原历史路线图，保留技术设想；当前不作为纯 PAD 版本的前置条件。待用户明确切换主线且获授权网络验证后再启动。


基线 V2 已实机 8 人；Core Lab 已实机报告。下一阶段不直接编写完整产品，先解决服务链路是否可用。

| 阶段 | 验收门槛 |
|---|---|
| 0 授权网络实验 | 由管理方明确允许客户端、服务及必要网络访问；在自有测试网络验证 |
| 1 Core Lab 连接 | 对指定获准服务完成 GET/POST、WS/WSS Echo；记录真实响应和错误，验证TLS证书 |
| 2 ESP32最小服务 | Wi-Fi、健康状态、资源记录；1个客户端双向消息，无 AI |
| 3 常驻房间 | 2→8人；任意客户端退出重开、重新认证、恢复授权历史；重复发送去重 |
| 4 持久化 | 重启、断电恢复、有限日志与容量；验证不影响聊天 |
| 5 iPad Console | 鉴权与角色拒绝测试；在线状态与操作审计 |
| 6 AI Gateway | 单个授权 API 调用；多请求队列、配额、取消、超时；AI失败不阻塞聊天 |
| 7 稳定性 | 8小时、24小时；2/8/16/32逐级测试，超容量拒绝；不能预先宣称通过 |
| 8 扩展 | 私聊、图片小文件、白板、投票、游戏，按需求逐个验收 |

记录指标：连接成功率、在线峰值、应用消息 ACK、真实跨设备 RTT p50/p95/max、丢失/重复/乱序、重连耗时、内部堆最小余量、PSRAM、最大队列、Flash 写入量、温度和复位原因。明确样本数、测试负载、网络与固件版本，区分回环/跨设备/ESP32。现有实测仅短时、8台操作者报告，不足以支持容量或 SLA 承诺。
